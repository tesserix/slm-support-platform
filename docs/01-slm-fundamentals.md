# 01 — SLM Fundamentals

## What is a language model?

A language model is a function that, given a sequence of tokens, predicts the probability distribution over the next token.

```
input:  "The customer is asking about their"
output: P(next_token | input)
        → "order"   0.31
        → "refund"  0.18
        → "account" 0.12
        → ...
```

That's it. Everything else — chatbots, agents, code generation — is built on top of this single primitive: *next-token prediction*. We train the model so this distribution matches the patterns in our training data, then we sample from it autoregressively to generate text.

## Small vs Large

The Small/Large divide is by parameter count, but the dividing line moves every year. The current useful bands:

| Class | Parameter count | Examples (2025/26) | Where it runs |
|-------|----------------|-------------------|---------------|
| **Tiny** (educational) | 1M – 100M | nanoGPT, TinyStories model, what we'll build | Single CPU / laptop GPU |
| **Small (SLM)** | 100M – ~8B | Phi-3-mini (3.8B), Llama-3.2 (1B/3B), Gemma-2 (2B), Qwen2.5 (1.5B), SmolLM | One mid-range GPU (T4/A10/L4) |
| **Medium** | 8B – 70B | Llama-3-8B, Mistral-7B, Llama-3-70B | One or a few A100/H100 |
| **Large (LLM/frontier)** | 70B – 1T+ | GPT-4, Claude, Gemini Ultra | Provider's data center |

"SLM" usually means **1B–8B parameters** — small enough to self-host on a single modern GPU, big enough to be useful with fine-tuning.

## Why an SLM for support chatbots (and not GPT-4)

The case for the small model isn't that it's "as good as" GPT-4. It isn't. The case is that **for a narrow domain**, a small fine-tuned model is competitive *and* dramatically cheaper, faster, and more controllable.

**Cost.** A support ticket answered by GPT-4 is roughly 1000 input tokens + 300 output tokens. At GPT-4 pricing that's ~$0.04. At 10k tickets/day across our products that's $400/day, $146k/year, just in inference. A self-hosted 3B model on one L4 GPU on GKE costs roughly $0.50/hour all-in, runs ~30 tickets/minute at <500ms latency. Math: about $13/day. Roughly 30× cheaper.

**Latency.** Cross-region API call to a hosted LLM is 1–3 seconds. An in-cluster SLM is sub-500ms. For a live chat widget, that's the difference between feeling instant and feeling broken.

**Data.** Customer messages may include PII, order details, payment context. Sending that to a third-party API has legal and contractual implications. An in-cluster SLM keeps it inside our VPC.

**Domain.** GPT-4 has never heard of `mark8ly` or `fanzone-battleground`. It can be prompted with context (RAG) but it can't be *fine-tuned* to know our products natively. An SLM can.

**Control.** When the model gets something wrong, you can fix it — retrain on corrected examples, add a tool, change the prompt, swap the retriever. With a closed API, you can only adjust the prompt.

## What the SLM is not good at

Be honest about the tradeoff so we don't oversell to ourselves later:

- **General knowledge.** A 3B SLM is *much* dumber about the world than GPT-4. If a customer asks "what's the capital of Australia," it might hallucinate. Mitigation: scope the chatbot to product support; out-of-scope queries get a polite redirect.
- **Complex multi-step reasoning.** Long chains of "if X then Y, but if Z then W" break down. Mitigation: keep agent steps short, use tools for anything stateful (DB lookup, API call), don't expect the model to do math.
- **Rare knowledge from pretraining.** SLMs forget the long tail. Mitigation: RAG. Anything in our docs, the model retrieves at runtime rather than relying on weights.

These limits define the system architecture in Phase 3: the SLM is the *language generator*, RAG is the *knowledge base*, the agent layer is the *control flow*. The SLM doesn't have to know everything — it has to *speak well* about what it's told.

## The from-scratch model in Phase 1

In Phase 1 we'll build a ~10–50M parameter decoder-only transformer (the same architectural family as GPT, Llama, Phi, Gemma — just smaller). Trained on TinyStories (~500MB of simple short stories generated by GPT-4) it will produce coherent, if childish, English text after a few hours on a single GPU (or a long afternoon on CPU).

This model is **not the production chatbot**. It exists so that by the time we touch Phi-3 or Llama-3.2 in Phase 2, you know exactly what's happening inside it — attention heads, KV cache, sampling temperature, gradient checkpointing — and not as buzzwords.

## What we won't build from scratch

To stay focused on the *learning* core, we'll use libraries for things that are well-understood and not pedagogically interesting:

- **PyTorch** for tensors, autograd, GPU kernels (writing matmul from scratch is a separate course)
- **HuggingFace `datasets`** for loading TinyStories
- We *will* implement the BPE tokenizer, attention, transformer block, training loop, and sampling ourselves — those are the parts where the understanding lives.
